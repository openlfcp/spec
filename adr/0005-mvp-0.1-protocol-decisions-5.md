# ADR 0005: MVP 0.1 protocol decisions, fifth batch

- **Status:** accepted, per item (see the Status column)
- **Decided by:** the orchestrator while the project owner was away (owner
  AFK; the owner asked the orchestrator to proceed autonomously). Approved
  by the project owner on 2026-10-06.
- **Applied by:** SPEC-PATCH-06 (baseline `mvp-0.1-baseline.6`)

## Context

Moving both SDKs to `mvp-0.1-baseline.5` (ALIGN-TS-5, ALIGN-RS-5) and the
network chaos suite (LFCP-057) showed where the Working Drafts were wrong
or silent: a rebuild that removed a writer's own change left the writer
unable to write again (LFCP-062), the G-DP1-GAP writer rule left re-applied stale work held at
every receiver, nothing required a client to retransmit after a lost reply,
"active invitation grant" was not tied to the §25.2 sense, the
scalar-string rule had no pointer-level vectors and no vector covered a
write to an object with a scalar conflict, and the Obsidian architecture
still suggested keeping plugin state in the vault-synced folder.

## Value changes

None. SPEC-PATCH-06 changes no published vector value; it only adds cases.
[`migrations/mvp-0.1-baseline.6/value-changes.json`](../migrations/mvp-0.1-baseline.6/value-changes.json)
lists no change, and `scripts/check-baseline-changes.mjs` fails on any
changed or removed value relative to `mvp-0.1-baseline.5`.

## Decisions

| ID | Status | Decision | Sections changed | Vectors |
| --- | --- | --- | --- | --- |
| WRITER-PREV | Approved by the project owner (2026-10-06) | A writer's `previous` is its latest own unit it still holds as accepted: published and not excluded by a cutoff (G-EP7) or as equivocation (G-DP5). After an abandoned, stale or equivocating unit at `N`, the next unit names `N-1`, so stale work re-applied in the current epoch (G-EP5) links. Replaces "last published" (G-DP1-GAP, ADR 0004) | LFCP-WIRE-01 §26.2 | none (the `actor_chain` cases cover the receiver) |
| REQ-LIVENESS | Approved by the project owner (2026-10-06) | A client that gets no answer to a request within an implementation-chosen timeout sends the same objects again in a new message, or issues the read again, with bounded backoff, without waiting for a reconnect; servers MUST answer a repeated object as the first time. Informative: Have Vectors describe accepted units only, so a held unit is not a hole | LFCP-WIRE-01 §70 | none |
| INVITE-READ | Approved by the project owner (2026-10-06) | "Active invitation grant" in the read rule has the §25.2 meaning (includes and still confers `invite/claim`). A used-up invitation grant no longer qualifies its subject to open or read; the subject then reads only through abilities it holds, such as a `data/read` the grant lists (§18.1). The Rust reference server behaves this way | LFCP-WIRE-01 §41 | none |
| SO-CONFLICT-WRITE | Approved by the project owner (2026-10-06) | A concurrent scalar conflict between two writers does not make an object profile-invalid; a later intent on another field succeeds and leaves the conflict reported | SHARED-OBJECTS-TEST-VECTORS-01 | new behavioral scenarios S15, S16 and their Automerge corpus entries |
| SO-STRINGS-POINTERS | Approved by the project owner (2026-10-06) | Collaborative Text anywhere in an object is `INVALID_FIELD_TYPE` at the Text value's own pointer, before the field's own rule (status, due, a tags member); the root `profile` as Text is `INVALID_ROOT`. JSON state fixtures cannot carry Text, so the cases are Automerge save images in the corpus | SHARED-OBJECTS-PROFILE-01 §30, §74.1 (vectors only) | new corpus `validations`: `SO-STRINGS-text-anywhere`, `SO-STRINGS-text-tag-member`, `SO-STRINGS-text-root-profile` |
| OWN-EXCLUSION | Approved by the project owner (2026-10-06) | A rebuild that removes the writer's own changes (its unit beyond a cutoff, its equivocating pair, or its change depending on an excluded one) is not lost state: the writer continues from the rebuilt document and may reuse a removed change's Automerge sequence number; it MUST NOT refuse to write. Receivers keep a change with missing dependencies outside the Automerge engine, and reject a change that skips its actor's sequence number (`INVALID_AUTOMERGE_BYTES`) before the engine sees it. Checked on Automerge JS 3.5.0 and automerge-rs 0.12.0: both refuse a duplicate (actor, seq) even against a pending change; automerge-rs aborts on a skipped sequence number. Which of two changes with the same actor and sequence number a replica keeps is left open | SHARED-OBJECTS-PROFILE-01 §9, §14.1, §74.1 | none |
| OBS-LOCAL-STATE | Approved by the project owner (2026-10-06) | Plugin state (Principal, keys, SDK storage) MUST NOT live under the vault-synced `.obsidian/` folder: IndexedDB, the device-level `secretStorage` and an install marker; `data.json` holds only non-secret preferences | `obsidian: docs/OBSIDIAN-ARCHITECTURE-01.md` §34 | none |

## Consequences

- Implementations move from `mvp-0.1-baseline.5` to `mvp-0.1-baseline.6`
  deliberately. No vector value changes; the S15/S16 scenarios and the
  corpus `validations` need runners.
- Writers link to their latest own unit still accepted; clients retransmit
  after a request timeout; a writer keeps writing after a rebuild removes
  its own changes.
- The owner approved every item on 2026-10-06. A later change would be a
  new batch with its own baseline.
